# 전체 흐름(End-to-End) 작업 기준

2026-08-16 세션에서 사용자가 지적한 패턴: LinPEAS 트리거, 파일·폴더 트리, 세션 재시작
버튼 같은 기능을 좁은 스코프 단위로 하나씩 구현했는데, 실제로 되는지는 매번 사용자가
라이브 세션에서 직접 부딪혀서 찾아내고("아무것도 안 되는데?", "버튼 누르면 명령어만
쌓이는데?") 하나하나 설명해줘야 했다. 이 문서는 그 지적("내가 하나하나 다 가르쳐줘야
하잖아")을 다음에 반복하지 않기 위한 기준이다.

## 트리거

"OO 박스 풀이에 필요한 기능/흐름을 만들어줘", "그래프에서 OO을 처음부터 끝까지 진행할
수 있게 해줘" 처럼, 특정 좁은 기능 하나가 아니라 전체 워크플로우(공격 체인)를 요청하는
경우.

## 원칙

1. **구현 전에 전체 체인을 먼저 그려본다** — recon → foothold → 쉘 안정화 → privesc
   정찰 → privesc 익스플로잇 → (필요하면) lateral/post-exploitation까지, 그 박스
   기준으로 실제 단계를 나열하고 그래프의 어느 노드·트리거·화면이 각 단계를 담당하는지
   매핑한다. "버튼 하나 추가"가 요청의 진짜 크기가 아닐 수 있다는 걸 먼저 확인하는
   단계다.
2. **끊기는 지점을 먼저 찾아 사용자에게 보고한다** — 매핑하다가 "다른 탭으로 옮겨야
   함", "복사→붙여넣기가 필요함", "그래프 노드 클릭만으로 안 되고 다른 워크스페이스로
   나가야 함" 같은 지점을 전부 목록으로 만들어, 구현 계획과 함께 먼저 제시한다. 이
   목록 없이 곧장 구현에 들어가지 않는다.
3. **구현 후엔 직접 브라우저로 전체 흐름을 걸어본다** — mock을 쓰는 단위 테스트는
   "버튼을 누르면 상태가 바뀐다"까지만 증명하지, 실제 셸·실제 대상에 대해 "그 기능이
   진짜 작동하는가"는 증명하지 못한다. 2026-08-16 세션에서 실제로 있었던 일: autoFloat
   터미널이 얼어붙은 props만 보고 있어서 LinPEAS 입력이 조용히 무시됨, 트리거를 연달아
   누르면 명령이 실행 안 된 채 쌓이기만 함, 파일 트리가 마커를 못 찾아 빈 채로
   "완료"됨 — 전부 단위 테스트는 이미 통과한 상태에서 라이브 검증으로만 잡혔다.
   브라우저 자동화 도구로 그래프에 들어가서 노드를 실제로 클릭하고, 세션을 실제로
   열고, 결과를 실제로 확인하는 과정을 처음부터 끝까지 직접 재현한 뒤에만 "됐다"고
   보고한다. `docs/OBVIOUSNESS_STANDARD.md` 원칙 4(실제로 실행해서 검증)의 워크플로우
   버전이다.
4. **박스 자체를 푸는 게 목적이 아니라 앱을 검증하는 수단이라는 경계는 그대로
   유지한다** — `CLAUDE.md`의 기존 원칙과 동일: 라이브 검증 중 크랙된 비밀번호, 플래그,
   root shell 같은 박스 진행 상황을 우연히 얻더라도 "이거 그래프에 반영할까요?" 같은
   1회성·부수적 제안을 스스로 꺼내지 않는다. 검증의 목적은 "그래프 UI가 이 단계를
   지원하는가"이지 "이 박스를 풀었는가"가 아니다.
5. **사용자가 QA를 대신하게 만들지 않는다** — 부분 기능을 던져놓고 사용자가 실사용하다
   깨진 걸 발견해서 설명해주는 구조로 되돌아가지 않는다. 원칙 3을 생략하면 정확히 이
   구조로 되돌아간다.
6. **"완료했다"는 스스로의 이전 보고를 그대로 믿지 않는다** — 코드가 존재한다는 걸
   확인했다고 해서, 사용자가 실제로 마주치는 첫 번째 버튼이 그 코드로 이어진다는
   보장은 없다(§ 적용 사례의 "Web Testing에서 열기" 사례). "이 기능 UI가 있다"와
   "사용자가 이 흐름에서 처음 누를 버튼이 그 UI로 이어진다"는 서로 다른 주장이며,
   후자만 원칙 3을 만족시킨다. 사용자가 재검증을 명시적으로 요구하면(예: "네가 일주일
   걸릴 일을 프롬프트 하나로 끝냈을 리 없다") 이전 세션의 "됐다" 보고를 재확인 없이
   전제로 삼지 않고, 처음 보는 사용자처럼 다시 클릭해본다 — 이 과정에서 코드 추적만으로는
   못 잡는 것(예: `window.prompt()`가 이 환경에서 조용히 실패하는 것, 눈에 띄는 CTA가
   전혀 다른 곳으로 내비게이션하는 것)이 실제로 나온다.

## 적용 사례

**HTB Oopsie/Archetype (2026-08-16 세션)** — 사용자가 "Oopsie랑 Archetype 완벽한
풀이 흐름 만들어놓고, 추가 입력 없이 판단해서 구현해"라고 요청. 원칙 1-2에 따라 먼저
공격 체인을 매핑하고 끊기는 지점을 코드로 확인한 뒤(단순히 "그런 기능이 있다"가 아니라
"그래프 UI 조작으로 거기까지 이어지는가"를 코드에서 직접 추적) 보고, 승인 후 구현:

- **쿠키 편집 불가** — Oopsie의 `role=0`→`role=1` 접근통제 우회에 필요. 백엔드는
  쿠키를 이미 지원했지만(httpx `cookies=`), 그래프에서 핸드오프되는
  `GraphRequestPanel.tsx`만 `cookies: {}`로 고정돼 있어 쿠키를 쓰려면 그래프 밖의
  전체 Web Testing 페이지로 나가야 했다 → 쿠키 편집 필드 추가.
- **멀티파트 파일 업로드 불가** — Oopsie의 웹셸 업로드 RCE에 필요. 웹셸 파일 자체는
  이미 만들 수 있었지만(`ReverseShellPanel`의 "업로드용 파일로 다운로드"), 그걸 실제
  업로드 폼에 POST하는 방법이 앱에 아예 없었다(`body_mode`가 raw/json/form뿐) →
  `body_mode: "multipart"` 추가(프런트 파일 선택 → base64 → 백엔드 httpx `files=`).
- **Windows PrivEsc 참고가 그래프에 없음** — Archetype의 PowerShell 히스토리 자격증명
  탈취(서비스 계정 비밀번호 = 도메인 관리자 비밀번호 재사용)에 필요. 정확히 필요한
  명령(`(Get-PSReadlineOption).HistorySavePath`)이 `credential_hunt.yaml`에
  **이미 있었지만** SSH/wmiexec 카탈로그 실행 전용이라, 그래프의 manual-shell/
  evil-winrm 세션에 열린 셸로는 보낼 방법이 없었다 — "명령이 존재한다"와 "그래프 UI
  조작으로 그 명령까지 이어진다"는 다른 질문이라는 걸 보여준 사례 → Linux와 완전히
  같은 패턴으로 `WindowsPrivescReference.tsx`를 만들어 Inspector의 manual-shell
  블록에 나란히 배치.
- **다시 시작 버튼 부재**(§ 이전 세션에서 이미 발견·수정) — 죽은 manual-shell 세션에
  재시작 버튼이 없던 것도 같은 유형: `retry()` 엔드포인트는 이미 범용이었는데 UI가
  Responder에만 붙어 있었다.

공통점: 넷 다 "이 앱에 관련 기능이 있는가"로 물으면 전부 예스였다. 실제로 막힌 질문은
"그 기능이 이 노드에서 클릭 몇 번으로 이어지는가"였고, 답은 셋 다 아니오였다. 원칙 1-2를
건너뛰고 "관련 기능 존재 여부"만 확인했다면 이 세 가지 모두 "이미 있음"으로 오판했을
것이다.

**같은 세션, 재검증 요청 ("네가 일주일 걸릴 일을 프롬프트 하나로 끝냈을 리 없다")** —
위 Oopsie/Archetype 구현을 "됐다"고 보고한 직후, 사용자가 그 보고를 믿지 않고 사용자
관점에서 버튼·편의기능을 하나하나 다시 검증하라고 요청. 원칙 6에 따라 실제로 빈 프로젝트를
새로 만들어 처음부터 클릭해보며 나온 것:
- **`window.prompt()`가 이 환경에서 조용히 실패** — `App.tsx`의 "+ 대상" 버튼을 눌렀더니
  브라우저 렌더러가 멈췄다(CDP 스크린샷 타임아웃). 코드를 열어보니 `AppShell.tsx`가 이미
  "bare/root Kali Chrome에서 `prompt()`/`alert()`는 아예 안 뜨고 조용히 실패한다"고
  문서화까지 해놨던 정확히 그 버그가 프로젝트 생성에서만 고쳐지고 대상 생성·대화형 인증
  이름 입력·스캔 alias/태그·동시 스캔 수·Runbook 복제 이름 5곳엔 그대로 남아있었다 —
  코드를 읽기만 해서는 안 잡히고 실제로 버튼을 눌러야만 잡히는 유형.
- **가장 눈에 띄는 버튼이 그래프를 이탈** — Oopsie 검증에서 만든 쿠키/멀티파트 지원
  `GraphRequestPanel`이 그래프 안에 잘 붙어있는 걸 이전에 확인했었지만, 사용자가 실제로
  맨 처음 누를 법한 "Web Testing에서 열기" 버튼은 `location.hash="web"`로 그래프를
  통째로 벗어났다. 그래프 내 경로는 `http-link-extract` 결과의 개별 링크 버튼에만
  숨어있었다 — "그 기능이 그래프 안에 있다"와 "사용자가 처음 누를 버튼이 그 기능으로
  이어진다"가 다른 주장이라는 걸 보여준 사례(원칙 6).
- **Unified 공격 체인 매핑에서 발견한, 구현하지 않기로 판단한 gap** — JNDI/rogue LDAP
  콜백 리스너(Log4Shell 실제 RCE 트리거)는 이 앱에 없고, exploit-db의 PoC 스크립트도
  깨진 상태였고 별도 JDK/marshalsec 바이너리 다운로드가 필요해 "외부 CLI 도구를
  감싼다"는 이 앱의 기존 패턴에서 크게 벗어났다 — 실제 대상 없이 검증도 불가능해 임의로
  구현하지 않고 gap으로만 보고했다. 판단을 위임받았다고 해서 검증 불가능한 큰 기능을
  무리하게 만들어 넣지 않는 것도 원칙 5(QA를 사용자에게 떠넘기지 않는다)의 연장선이다.

## 적용 방법

- "OO 박스 풀이 기능/흐름 만들어줘" 같은 요청을 받으면 곧장 구현에 들어가지 않고,
  원칙 1-2에 따라 계획과 끊기는 지점 목록을 먼저 제시한다.
- 사용자가 승인하면 구현하고, 원칙 3에 따라 브라우저로 직접 전체 흐름을 재현해 검증한
  뒤 결과를 보고한다.
- "브라우저에 들어가서 확인해볼 수 있어?" 류의 질문은 반드시 실행해도 되냐는 확인이
  아니라 능력을 묻는 질문일 수 있다 — 곧바로 실행하지 말고, 먼저 답하고 진행 여부를
  확인한다.
- 이 문서도 정적 체크리스트가 아니다 — 다음에 비슷한 요청에서 새로 발견되는 원칙·사례가
  있으면 추가한다.
