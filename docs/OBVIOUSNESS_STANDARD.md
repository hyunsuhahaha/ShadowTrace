# "당연함" 기준

2026-08-14 세션에서 사용자가 반복적으로 "이거 당연히 되어 있어야 하는 거 아니야?"라고
지적했고, 매번 실제로 재현 가능한 버그였다(추측이나 과민 반응이 아니었다). 이 문서는 그때
찾은 사례와, 다음 세션이 사용자가 다시 설명하지 않아도 같은 기준으로 스스로 감사(audit)할
수 있도록 정리한 원칙이다.

## 이 세션에서 발견된 사례

1. `service-version` catalog 명령 설명: "관찰된 값을 이 서비스에 자동 저장합니다." —
   백엔드(`executor.py`)는 실제로 저장하지만, 그래프 Inspector는 raw stdout만 보여줘서
   사용자가 직접 읽고 판단해야 했다. 같은 문구를 쓰는 다른 5개 명령
   (`telnet-info`, `telnet-version-trace`, `database-info`,
   `target-hostname-redirect`, `target-hostname-identity`, `target-os-identity`)도
   전부 같은 상태였다.
2. 그래프에 파일을 노드로 올려도(zip 다운로드) 압축 해제·내용 확인 수단이 전혀 없었다 —
   `/api/evidence/{id}/file` 다운로드만 있었고, 이 앱에 이미 있는 zip2john
   (Hash Cracking)조차 연결돼 있지 않았다.
3. post-exploitation 파일 트리에는 이미 "드래그해서 그래프 노드로 추가" 기능이 있었지만,
   구조적으로 똑같은 zip 멤버 목록·FTP 다운로드 목록에는 없었다(클릭 버튼만 있었음).
4. zip2john이 뽑은 해시의 hash-mode 자동 선택 로직이 다중 파일 zip을 처리하지 못했다 —
   문자열 형태(`$pkzip$` vs `$zip2$`)만 보고 만든 추측이었고, 실제로 hashcat을 돌려본
   적이 없어서 발견되지 않고 있었다. 모드를 고쳐도 여전히 실패했다 — 이 환경의 소프트웨어
   OpenCL(Mesa llvmpipe/rusticl)이 PKZIP 커널의 self-test를 통과하지 못하는 별개의 층이
   하나 더 있었고, 이것도 직접 hashcat을 돌려보고서야 잡혔다(같은 사례 안에서도 "고쳤다고
   생각한 원인"과 "실제 원인"이 다를 수 있다 — 재검증까지 끝나야 끝난 거다).
5. 파일 선택 `<input type="file">`이 고른 직후 `e.target.value = ""`로 즉시 리셋돼서,
   브라우저 자체가 그려주는 "선택된 파일: X" 표시가 업로드 내내 절대 뜨지 않았다.
6. hashcat 모드까지 다 고쳤는데도 계속 실패했다 — 실제 원인은 두 가지 다른 버그였다:
   (a) 모든 크랙 작업이 `--session` 없이 hashcat 기본 세션 이름을 공유해서, 한 작업이
   실행 중일 때 다른 작업을 시작하면(해시·모드가 전혀 무관해도) "Already an instance
   running"으로 즉시 실패했다 — 그리고 그 "먼저 실행 중이던 작업"은 바로 이전 사례를
   라이브 검증하며 내가 백그라운드에 남겨둔 것이었다. (b) "크랙 시작"을 눌러도 방금 만든
   작업으로 화면이 안 넘어가고 사용자가 작업 이력에서 직접 클릭해야 했다 — `history` 쿼리가
   아직 리페치되기 전의 stale render에서 "현재 선택된 작업이 목록에 없다 → 가장 최근 것으로
   되돌리기" effect가 그 방금 만든 작업을 다시 밀어냈기 때문이었다.
7. 사례 5의 첫 수정이 스스로 이 문서가 경고하는 실수를 저질렀다 — 네이티브 "선택된 파일
   없음" 텍스트는 그대로 둔 채 파일명을 보여주는 새 엘리먼트를 옆에 하나 더 추가했다.
   사용자가 가리킨 그 자리는 여전히 안 바뀌어서 "고쳤다며?"라는 재지적을 받았다. 네이티브
   input을 숨기고 트리거 전체를 상태 기반으로 다시 그려서야 실제로 고쳐졌다.
8. nmap이 자동으로 만든 "Ftp Anon on {ip}:{port}" finding 후보에 "익명으로 접속하기"
   버튼이 없어서 사용자가 직접 FTP 명령을 찾아 타이핑해야 했다 — host/port는 그 finding의
   제목 자체에 이미 있는데도. 같은 턴에 `ftp-directory-tree`(및 형제 4개 프로토콜)의 실행
   결과도 raw `F|backup.zip` 텍스트로만 보여줬다 — 전용 tree 렌더러(`FileTreeView`, 폴더
   아이콘 포함)가 이미 있고 그 출력 형식이 그 렌더러용으로 설계됐다는 게 스크립트 자기
   주석에 쓰여 있었는데도 연결이 안 돼 있었다. 그리고 그 트리에 뜬 파일을 실제로 받을
   방법이 아예 없었다(목록 스크립트 자체가 다운로드 기능이 없음) — 사용자가 수동으로 `get`을
   타이핑하다 오타(bazkup.zip)를 내서 조용히 실패한 게 "왜 노드에 안 뜨냐"는 원래 질문의
   진짜 원인이었다. 셋 다 같은 근본 패턴: 정보는 이미 시스템에 다 있는데(제목의 host/port,
   이미 만들어진 tree 렌더러, tree가 이미 찾아낸 파일 경로) 그걸 실제 행동으로 연결하는
   마지막 한 걸음이 빠져 있었다.
9. 사례 8에서 고친 "익명으로 접속하기" 버튼이 만든 세션이, 그래프에서는 그 finding의
   자식이 아니라 루트(host) 밑에 붙었다 — 버튼을 누른 자리(그 finding)와 결과가 뜨는
   자리(host 바로 밑)가 달라서, 그 세션 안에서 `get`한 파일이 어디에 반영되는지 사용자가
   찾을 수 없었다. 근본 원인은 세션 동기화 로직(`sync_from_project`)이 항상
   `parent_of(service_id, target_id)`로만 부모를 정했고, "이 세션은 특정 finding에서
   시작됐다"는 정보를 애초에 받지도 저장하지도 않았던 것 — `promote_download`/
   `promote_file` 등 "파일을 노드로 승격"하는 다른 모든 엔드포인트는 진작에
   `graph_node_id`로 부모를 지정받는데, "세션을 만드는" 엔드포인트만 그 패턴이 없었다.
   같이 확인해보니 "폴더·파일 트리 자동 조회"도 이미 존재했지만(`_auto_run_ftp_tree`)
   데스크톱 터미널로 열 때만 실행됐고, 웹 터미널(익명 접속 버튼이 쓰는 경로)에는 연결이
   안 돼 있었다 — 있는 기능이 특정 진입 경로에서만 빠진, 사례 3과 같은 유형. 사용자가
   "당연히 후자지"(모든 수동 FTP 세션에 적용)라고 확인해준 뒤, 세션 생성 엔드포인트
   하나로 자동 조회 트리거를 통합하고, 그 결과를 세션 자신의 Inspector 안에 바로
   보여주도록(별도 "폴더·파일 트리 조회" 결과 노드를 따로 찾아갈 필요 없이) 만들었다.
   라이브 검증 중에는 이 세 가지 모두(계층 구조, 자동 트리, get 승격)가 코드는 맞는데
   화면에 안 뜨는 것처럼 보이는 순간이 있었다 — 원인은 버그가 아니라 자동화된 브라우저
   탭이 background 상태로 간주되면서 React Query의 `refetchInterval`이 억제된 것이었고,
   노드를 한 번 벗어났다 다시 선택하면(즉 마운트 시 최초 fetch가 다시 실행되면) 정상
   표시됐다 — "화면에 안 보인다"고 바로 버그로 단정하지 말고, 최초 마운트 fetch로
   재현되는지 먼저 확인해야 폴링 타이밍 이슈와 진짜 버그를 구분할 수 있다.

## 원칙

1. **약속 감사(Promise Audit)** — 카탈로그 설명, docstring, 주석이 "자동으로 X 합니다"
   같은 명시적 약속을 하면, 그 약속이 실제로 화면에 보이는지 확인한다. 안 보이면
   "편의 기능 부재"가 아니라 **버그**다. 백엔드가 실제로 그 일을 하고 있는지(DB가 갱신되는지)
   와, 그 결과를 사용자가 UI에서 실제로 볼 수 있는지는 별개의 질문이며 **둘 다** 확인한다.
2. **패턴 전수조사** — 하나의 인스턴스에서 이런 버그를 찾으면 그 하나만 고치고 끝내지
   않는다. 같은 문구·같은 코드 구조를 가진 다른 모든 인스턴스를 `grep`으로 찾아 전부
   고친다(사례 1이 정확히 이렇게 5개 더 나왔다).
3. **기존 UX 패턴의 일관 적용** — 한 영역에 이미 구현된 편의 기능(드래그 추가, 다운로드
   링크, "확인됨" 요약 패널 등)이 있다면, 구조적으로 비슷한 다른 목록·노드 종류에도 같은
   기능이 있는 게 "당연"하다. 없으면 찾아서 갖춘다. 단, 완전히 새로운 종류의 기능을
   만드는 것과는 구분한다 — 이미 있는 패턴을 넓히는 것이지 새로 설계하는 게 아니다.
4. **실제로 실행해서 검증** — "말이 되는 것 같은" 코드(문자열 형태만 맞춰 만든 로직 등)를
   작성했다고 끝내지 않는다. 가능하면 실제 도구(hashcat, nmap 등)를 직접 돌려서 결과를
   확인한다. 이 세션에서 사례 1(자동 저장 여부)과 사례 4(hashcat 모드)를 둘 다 이렇게
   — DB를 직접 조회하고, hashcat을 직접 실행해서 — 잡았다. 코드를 읽는 것만으로는
   "그럴듯해 보이는" 버그를 못 잡는다.
5. **버그 vs 미완성 롤아웃 구분** — 모든 격차가 "거짓말"은 아니다. "설명과 다르게 동작"하는
   것(자동 저장 안 함, 크랙이 항상 실패함)과 "아직 다 이식되지 않은 편의 기능"(6개 프로토콜엔
   있는 "확인됨" 패널이 8개 프로토콜엔 아직 없음, 원본 데이터는 노드를 직접 클릭하면 여전히
   보임)은 다르게 취급한다 — 전자는 즉시 고치고, 후자는 규모를 사용자에게 알리고 진행 여부를
   확인한다. 다만 승인받으면 주저 없이 진행한다.
6. **사용자가 가리킨 그 자리를 직접 고친다** — "여기가 틀렸다"는 지적에 옆에 새 엘리먼트를
   추가하는 걸로 답하지 않는다. 원래 있던(깨진) 표시를 대체해서, 정답이 하나만 존재하게
   만든다. 두 개의 서로 다른 답(하나는 고쳐졌고 하나는 여전히 깨진)이 같은 화면에 남아있으면
   사용자 입장에선 "안 고쳐진 것"과 구분이 안 된다.
7. **라이브 검증 후 뒷정리** — 실제 서비스(hashcat, 장시간 스캔 등)를 돌려서 검증했다면,
   백그라운드에 남겨두지 말고 취소/중단한다(사례 6이 정확히 이렇게 발생했다 — 검증용으로
   띄워둔 작업이 사용자의 다음 진짜 시도를 막았다). 라이브 검증은 증거를 남기되 흔적은
   남기지 않는다.

## 적용 방법

- 사용자가 "이거 왜 안 해놨어?" / "당연한 거 아니야?"라고 물으면, 방어하거나 설명만 하지
  말고 위 원칙에 따라 즉시 감사하고 고친다.
- 사용자가 먼저 묻지 않아도, 비슷한 기능을 구현하거나 기존 코드를 손댈 때마다 "이 패턴이
  이 코드베이스 다른 곳에도 있는가?"를 스스로 확인한다.
- 이 문서는 정적 체크리스트가 아니다 — 다음 세션에서 같은 유형의 새 사례를 찾으면 위
  "발견된 사례" 목록에 추가한다.
